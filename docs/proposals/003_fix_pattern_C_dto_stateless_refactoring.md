# 修正計画パターン C：環境変数への依存脱却（DTO化）パターン (DTO & Stateless Refactoring)

## 1. 概要
`GEMINI_SYSTEM_MD` や `OPENCLAW_SESSION_KEY` のような「リクエストごとのコンテキストデータ」を、グローバルな状態である `process.env` を介して渡すことを全面的に廃止し、Gemini CLI コアの API 引数や `settings` オブジェクトの動的オーバーライドとして注入する、根本的なアーキテクチャ昇華アプローチです。

## 2. 背景と解決するメカニズム
そもそもプロセス起動後に `process.env` を動的に書き換える（ミューテーションする）こと自体が、状態管理においてバグを引き起こしやすいアンチパターンです。
現在、システムプロンプトのパスを環境変数（`GEMINI_SYSTEM_MD`）経由で渡していますが、これは Gemini CLI コアが環境変数からこれを読み取る仕様に依存しているためです。この依存を断ち切り、Data Transfer Object (DTO) として純粋な引数でコンテキストを渡すべきです。

## 3. 実装の方向性
- **`src/server.js` の改修**:
  環境変数の生成・送信を完全に廃止し、IPC メッセージの明確なプロパティとしてコンテキストを送信します。
  ```javascript
  // 送信ペイロードの明確化
  runnerPool.acquireRunner({
      input: promptText,
      // env: env, // <- 廃止
      systemMdPath: tempSystemMdPath,
      sessionKey: sessionKey,
      // ...
  });
  ```

- **`src/runner.mjs` の改修**:
  環境変数の書き換えを全廃します。その代わり、Gemini CLI の `runNonInteractive` に渡す `config` や `settings` オブジェクトに対して、受け取ったプロパティを直接注入・オーバーライドします（※ Gemini CLI コアがプログラムからのプロンプト注入をサポートしているかを調査・活用する必要があります）。
  もしコアが環境変数しか受け付けない仕様である場合は、`fs` モジュールを用いてシステムプロンプトの中身自体を `resumedSessionData` などの安全なインメモリ履歴の先頭要素として直接流し込む形にリファクタリングします。

## 4. 評価
- **メリット**:
  - グローバルな状態（`process.env`）のミューテーションがゼロになり、プログラムの堅牢性とテスト容易性が極限まで高まります。
  - 将来、Runner プロセスを「使い捨て」から「マルチターン常駐型」に進化させる場合でも、状態の混入（コンテキスト・リーク）が起こりません。
- **デメリット**:
  - Gemini CLI コア（`@google/gemini-cli-core`）の API 仕様に深く依存するため、引数からシステムプロンプトを注入できるかどうかの追加調査が必要です。実現難易度が最も高い可能性があります。
