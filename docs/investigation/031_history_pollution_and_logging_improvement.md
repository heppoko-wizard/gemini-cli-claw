# 調査レポート：履歴汚染（ツールログ混入）とデバッグトレーサビリティの改善 (Fact Finding Report)

## 1. 調査目的
SSoT 5.1 実装後も会話履歴にツールログ（⚙️）が混入する事象（履歴汚染）の原因を特定する。
また、Gemini CLI からの生出力とアダプターの処理結果を可視化するデバッグモードの設計に向け、現状のトレーサビリティを調査する。

---

## Phase 1: 調査計画 (Phase 1: Investigation Planning)

### 1-1. 現状の把握
- **事象**: `streaming.js` にて思考・ツールログを `reasoning_content` に分離したが、履歴にツールログが登場している。
- **懸念**: 
  - `streaming.js` 内で `content` にも書き込んでしまっている可能性。
  - `server.js` の `Total Cleansing` ロジックが最新の `⚙️` 形式（Markdownブロック/バックタプル）に対応しておらず、履歴再構築時に消去できていない可能性。
  - OpenClaw 側での `reasoning_content` の扱い（履歴保存時に強制的に `content` にマージしている等）。
  - デバッグ用のログが不足しており、上記の切り分けが困難。

### 1-2. 調査ステップ
1.  **ソースコード再精査 (`streaming.js`)**: 
    - `case 'tool_call_request'` および `case 'thought'` 内で `delta.content` が呼ばれていないか。
2.  **履歴クレンジングの精査 (`server.js`)**:
    - `Total Cleansing` の正規表現が `⚙️ **tool_name**\n\`\`\`json...` の形式を網羅しているか。
3.  **生データダンプ機能の検討**:
    - `runner.mjs` または `streaming.js` で、受信した IPC メッセージ (`gemini_event`) をそのままファイルに追記する仕組みの導入可否。

【追加の議論と検証ループ】
- **議論/指摘**: 
  - ユーザーより「パースエラーか何かで会話履歴に tool が登場している」との指摘。
  - 「⚙️ とかアダプタ側で無耽な加工をするな」という強い指示。
- **新仮説3**: 
  - `streaming.js` が `reasoning_content` に送っている `⚙️ **tool_name**...` という装飾テキストが、OpenClaw 側の履歴保存ロジックによって `assistant` の `content` にマージされ、次ターンのリクエストでアダプターに送り返されている。
  - 現在の `server.js` には、この新しい装飾形式（Markdown形式）を消去するロジックが存在しないため、履歴が汚染されたまま Gemini CLI に渡され、ループや重複表示を引き起こしている。
- **検証**:
  1. `src/streaming.js` の `tool_call_request` ハンドラを確認。 -> 実際に `⚙️` や Markdown 記述が存在する。
  2. `src/server.js` のクレンジング処理を確認。 -> `⚠️ [Gemini API Error]` しか消しておらず、`⚙️` はスルーされている。
- **再検証と事実**:
  - `streaming.js` L270: `const toolLog = \`⚙️ **${tc.name}**\\n\\\`\\\`\\\`json\\n${argsStr}\\n\\\`\\\`\\\`\`;` と実装されている。これが「無駄な加工」の正体。

---

【調査の最終結論】
1. **履歴汚染の真因**: `streaming.js` が `reasoning_content` に送付している `⚙️ **tool_name**` という装飾済みテキストが、次ターンの履歴リクエストにて `content` として戻ってきている。現在のアダプターにはこれを消去するロジックがないため、履歴が汚染され続けている。
2. **加工の排除**: ユーザーの指示通り、アダプター側での `⚙️` や Markdown 装飾は一切不要である。生の情報を最小限の形式で送るべき。
3. **トレーサビリティ不足**: `logs/` ディレクトリが Docker 側でボリュームマウントされていないため、ホスト側からデバッグ用の `adapter_last_req.json` や `raw_req.bin` にアクセスできない。

【解決に向けた提案】
- `src/streaming.js`: ツール出力の装飾を撤廃し、純粋なログ形式のみを出力する。
- `src/server.js`: 過去の `assistant` メッセージから、装飾済みツールログ（および新規の簡易ログ）を完全に除去する強力なクレンジング正規表現を実装する。
- `docker-compose.yml`: `logs/` ディレクトリをホストにマウントし、デバッグの透明性を確保する。
