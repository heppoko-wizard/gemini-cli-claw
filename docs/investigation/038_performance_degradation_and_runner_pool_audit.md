# 調査レポート：パフォーマンス低下とランナープールの動作確認 (Investigation Report)

## 1. 調査目的
SSoT 6.1/6.2 実装以降、応答速度が著しく低下したとの報告。新機能（ファイルベースの永続化など）によるオーバーヘッド、または Runner Pool のウォームアップが正常に機能していない可能性を事実に基づき特定する。

---

## 2. 調査計画 (Investigation Plan)

### 現状の把握
- 現象: 応答速度の極端な低下。
- 疑い: Runner Pool のウォームアップ無視、あるいはファイル I/O のオーバーヘッド。

### 調査ステップと手順
1.  **ランナー取得ロジックの再確認 (`src/streaming.js`)**:
    - `runGeminiStreaming` 内で `RunnerPool.acquireRunner` が正しく呼び出されているか、非効率な起動が行われていないかを確認。
2.  **ログによるタイミング分析 (`logs/adapter.log`)**:
    - `[Pool] Runner is ready` からリクエスト受信、最初のトークン送出までのタイムスタンプを分析。
    - `[tool-store] Persisted context` や `[history] Rehydrating tool` にかかる時間を特定。
3.  **環境設定の確認 (`docker-compose.yml`, `start.sh`)**:
    - ランナープールのサイズ設定や起動オプションに変更がないか確認。

---

## 3. 調査の道筋（仮説と検証のトレイル）

### 3-1. 仮説1：Runner Pool のウォームアップが機能していない
- **検証**: `logs/adapter.log` を確認し、`Spawning` ログとリクエストの重なり方を調査する。

### 3-2. 仮説2：ファイルベースの永続化（SSoT 6.1）による I/O 遅延
- **検証**: `storeToolContext` や `loadToolContext` の実行前後にログを仕込む（または既存ログのタイムスタンプを確認する）。

---

## 4. 事実の発見 (Fact Finding)

### 4-1. ランナープールのウォームアップと環境の不一致
- **事実**: `src/runner-pool.js` は、共通の隔離ディレクトリ `/app/gemini-home` を `GEMINI_CLI_HOME` としてランナーを事前起動（Warm up）している。
- **事実**: `src/runner.mjs` は起動直後（L13, L15）に `loadSettings()` と `loadCliConfig()` を実行し、メモリ上に設定をロードする。この時点では `/app/gemini-home` の設定が読み込まれている。
- **不整合の発見**: `src/server.js` はリクエストごとに `prepareGeminiEnv` を呼び出し、セッション個別のディレクトリ（`/app/gemini-home/gemini-sessions/{sessionKey}`）を `GEMINI_CLI_HOME` として生成し、IPC でランナーに渡している。
- **影響**: `runner.mjs` は IPC で新しい `env` を受け取るが、**設定情報を再ロードしていない**。そのため、セッション個別の設定（MCP サーバー引数など）が無視されている、あるいは古い設定と新しいセッションデータの矛盾により `runNonInteractive` 内で非効率な処理が発生している可能性がある。

### 4-2. リクエストごとの重複する準備処理
- **事実**: `src/server.js` (L374) にて、ストリーミング・非ストリーミングを問わず、全リクエストで `prepareGeminiEnv` が呼び出されている。
- **内容**: この関数はディレクトリ作成、`settings.json` の書き込み、認証ファイルのコピーを毎回実行しており、ファイル I/O のオーバーヘッドが蓄積している。

### 4-3. 異常終了ログの特定
- **事実**: `adapter.log` にて `Runner consumed (exited with code 42, signal null)` を確認。
- **意味**: `ExitCodes.FATAL_INPUT_ERROR (42)` は、ランナーが実行中に何らかの致命的エラーで落ちたことを示す。環境の不整合により、Gemini CLI が期待するセッションデータや設定を読み込めず、エラー終了と再起動のループが発生していた可能性がある。

---
## 5. 調査結果のまとめ
応答速度低下の主な原因は、**「ウォームアップ済みランナーが、実行時に渡されたセッション個別の環境（GEMINI_CLI_HOME）を正しく反映（再ロード）できていないこと」**に起因する非効率性と、リクエストごとの重いディスク I/O 処理の重複にあると判断される。
また、この不一致が原因でランナーがエラー（Code 42）で頻繁に終了し、プールの補充（再起動）が頻発して「ウォームアップが効いていない」状態を作り出している。
