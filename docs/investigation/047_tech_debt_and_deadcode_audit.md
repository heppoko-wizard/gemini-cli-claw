### 調査レポート：残存する不要コードと技術的負債の調査

【調査の道筋（仮説と検証のトレイル）】
- **仮説**: 今回の Persistent Runner（常駐型プロセスの導入）および Docker の最適化（マルチステージビルド化・Nodeへの一本化）に際し、以前の Disposable Runner（使い捨てプロセス）や Bun の並行運用を前提とした不要なコード、あるいは繰り返しの改修でスパゲティ化している部分が残存しているはずである。
- **検証**: `runner-pool.js`, `streaming.js`, `runner.mjs`, `server.js` を `view_file` で閲覧し、ロジックの使われ方やコメント、関数の生存状態を確認した。

- **事実の発見1 (`src/runner-pool.js` における「寿命管理」の残骸)**:
  - 過去の「使い捨てRunner」時代は、特定の時間が経過した待機プロセスを殺す（kill）ロジックが不可欠だった。
  - 現在の実装では、`releaseRunner` により同じプロセスが半永久的に再利用される設計になっているにも関わらず、L249付近に `setInterval` を用いた `_cleanupOldRunners` などのプロセスクリーンアップロジックが中途半端に残り、不要なポーリングオーバーヘッドを生んでいる。
  
- **事実の発見2 (`src/streaming.js` における「偽の要約応答」コードの残留)**:
  - OpenClaw の要約プロンプトをインターセプトする処理について、以前はアダプター側で**固定の嘘の要約文（sendFakeSummaryResponse）**を返すハックが使われていた。
  - 現在は Gemini CLI へ処理を委譲（SSoT 4.0〜）しているため完全に不要だが、`src/server.js:65-100` 付近に `sendFakeSummaryResponse` の巨大なコメントアウトブロックがそのまま残置されており、可読性を低下させている。

- **事実の発見3 (`src/server.js` および `src/streaming.js` における「レガシーSSoT」のクレンジング負債)**:
  - SSoT 6.0 への移行により、ツール実行のログはプレーンなマーカー（`⚙️ tooluse[name][id]`）になった。
  - しかし、`src/server.js:213-228` 付近には、それ以前の SSoT 5.1 時代に使われていた Markdown ブロック式のレガシーな偽ツールログ（`⚙️ **toolname**\n```json...```）を取り除くための重い正規表現（`legacyToolLogRE`）が、すべてのリクエスト履歴に対して依然として実行されている。これは新規セッションにおいては完全に不要なCPUの浪費（スパゲティ化の一端）である。

- **事実の発見4 (`start.sh` や `docker-compose` 周辺の環境変数の名残)**:
  - Bun を使用するための `BUN_INSTALL` などのパス設定やフラグ定義が、他のスクリプト（特に `rebuild.js` や旧セットアップ系のバッチ）に中途半端に残っている可能性がある（本調査では主要ソースコードのみにフォーカス）。

【コードベース・仕様から確認された最終的な事実】
- `src/runner-pool.js` には、常駐型プロセスと相反する「プロセスの寿命監視・クリーンアップ」用のデッドコードが残存している。
- `src/server.js` には、旧アーキテクチャのハックであった数十行の関数がコメントアウトのまま残置され、また、旧フォーマットの巨大データを消し去るためだけの正規表現置換（レガシークレンジング処理）がすべてのリクエストに対して無条件で実行されている。
