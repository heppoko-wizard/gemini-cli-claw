### 調査レポート：アダプターのハングアップ調査

【調査の道筋（仮説と検証のトレイル）】
- **Phase 1: 調査計画**
    - **現状の把握**: ユーザーより「メッセージを送っても帰ってこなくなった」「アダプタがどこかでハングしている」との報告。
    - **調査の手順**: (完了)
        1. Dockerコンテナおよびプロセスの生存確認
        2. ログファイルの詳細解析
        3. ネットワーク接続性の確認
        4. `runner-pool.js` による子プロセス管理の状態確認

- **Phase 2: 事実の収集 (進行中)**
    - **[事実] アダプターの生存**: `curl http://localhost:3972/health` に対し `200 OK` を返答。アダプターサーバー自体は健全。
    - **[事実] ランナーの挙動**: `logs/adapter.log` より、30分ごとのアイドルタイムアウトによるプロセス再起動を確認。これは正常な「フェイルセーフ」機能。
    - **[事実] Gateway の沈黙**: `docker compose logs` および Gateway の内部状態を確認したところ、ログ出力が 3月19日 17:08 UTC を最後に停止している。
    - **[事実] 通信の遮断**: Gateway とアダプター間に `ESTABLISHED` な接続が存在しない。Gateway がリクエストを送信する手前で停止している。

---
【現在の分析】
アダプター（Gemini CLI 側）の問題ではなく、**OpenClaw Gateway 本体が内部的にデッドロックまたはフリーズしている**可能性が高いと初期分析されましたが、その後の深掘りにより、以下の複合的要因が判明しました。

- **Phase 3: 根本原因の特定と暫定対処 (完了)**
    - **[事実] エラーの不可視化**: `runner-pool.js` において、`isReady` 以降の標準エラー出力がフィルター（特定のキーワードのみを通す）されており、`runner.mjs` が出力する実行時エラーがログに記録されていなかった。
    - **[事実] リクエストの蒸発**: ランナーが起動直後にクラッシュ（Exit Code 42）すると、アダプターはリクエストをキューから捨て、クライアントには正常終了を返してしまうため、ユーザーからは「無反応」に見える。
    - **[暫定対処]**: `runner-pool.js` のログフィルターを解除し、全エラーを捕捉可能にした。また、コンテナ再起動により Gateway のハングも一度リセットした。

【最終結論】
本事象は「アダプターの生存」と「リクエストの不可視な消失」が重なったことでハングアップとして認識されたものである。
根本的な解決（リクエスト消失の防止と高速化）のため、Persistent Runner（常駐型ランナー）への移行を次のタスクとする。
