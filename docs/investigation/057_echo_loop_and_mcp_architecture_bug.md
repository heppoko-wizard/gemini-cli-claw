### 調査レポート：[LLMメッセージ重複・無限ループ（エコー）問題の根本原因調査]

【調査の道筋（仮説と検証のトレイル）】
- **仮説**: Docker コンテナ内部にて LLM がメッセージを二重・三重に重複送信し、場合によっては無限ループを引き起こす原因は、LLM 自身の「自己暗示（Degenerate Repetition）」によるものであると考えた。
- **検証**: `/root/.openclaw/workspace/memory-injected` などの Gateway 側のコンテキスト履歴ファイルを抽出し、内容を確認した。
- **事実の発見**: LLM 自身が「エコーループが起きている」とメタ認知し、その「エコーがある状態」の文脈を毎ターン引き継いで自己増幅している記録を発見した。

【追加の議論と検証ループ】
- **議論/指摘**: ユーザーより「3度コンテキストをリセットしても再発した。昨日までは起きなかった。昨日のCLIとのやり取り（MCP周り）やアダプターの根本的構造変更で混入したシステム的バグの可能性が非常に高い」との強い指摘を受けた。これを基に LLM の自己暗示は「結果」であり「原因」ではないと判断。
- **新仮説**: 2026-03-20 に導入した「Persistent Runner（常駐ランナー）」アーキテクチャや、「mcp-server-lightweight.mjs」への移行に関連して、以下のいずれかの物理的なシステムバグが混入した。
  1. `EventEmitter` などのイベントリスナーがリクエスト毎に解放されず蓄積し（リスナーリーク）、1回の AI の出力を 2回、3回、N回と重複してクローン中継している。
  2. MCP サーバー（Gateway 側）と Adapter 間での双方向通信において、何らかの終了判定ミスや再送ロジックのバグにより通信の無限往復（システムレベルのエコー）が発生している。
- **調査計画**:
  1. `git diff` を用いて、昨日（2026-03-20）実施された `src/runner.mjs`、`src/streaming.js`、`src/runner-pool.js`、および `mcp-server-lightweight.mjs` の変更履歴から事実となるコードを確認する。
  2. 特に `geminiClient.sendMessageStream` のインターセプト部分や `on('message')` などのイベント登録箇所に、`removeAllListeners` や `once` の欠落がないか（現状の記述内容）を確認する。

【コードベース・仕様から確認された最終的な事実】
1. **Persistent Runner (常駐プロセス) の状態リーク**:
   - `git diff` および `src/runner.mjs` のコード現状を確認した結果、2026-03-20 に導入された `RunnerPool` アーキテクチャにより、1つの Node.js プロセス内で `config` や `geminiClient` のインスタンスがリクエストを跨いで再利用（ステートフル化）されている事実を確認しました。
   - 従前の使い捨てプロセス（Stateless）では毎リクエスト環境がリセットされていましたが、現在は生きているプロセスに対し、毎ターン OpenClaw(UI) 側からフルの会話履歴 (`resumedSessionData`) が注入されます。これが既存のメモリ・データベース上のセッションとマージ（累積追記）され、プロンプト履歴が『元の履歴 ＋ (元の履歴＋新発言) ＋ (元の履歴＋新発言＋新回答) ...』のように倍々ゲームで無限増殖し、LLMからは「全く同じ発言が二重三重に木霊（エコー）している」ように見えてしまう（そしてエコー状態に自己言及した回答を繰り返す）ことが、本現象の全ての根本原因です。
   - **対策済**: `runner.mjs` にて `prompt_id` に基いたエフェメラルなセッションIDを強制付与することで、Gemini側からは毎リクエストが「常に新規セッション」として扱われるように隔離し、歴史の自己増殖を物理的に遮断しました。

2. **イベントリスナーのメモリリークの副次的発見**:
   - `src/streaming.js` の `runGeminiStreaming` 内において、`runner.stdout.on('data')` と `runner.stderr.on('data')` が毎リクエスト登録されたまま破棄（`removeListener`）されておらず、単一の出力に対して N個分のログ出力が行われる（`adapter.log` が肥大化する）別のバグも同時に特定しました。
   - **対策済**: リスナーに関数名を付与し、ストリーミング終了時（`close` / `error` / `complete`）に明示的に `removeListener` を行う「クリーンアップ・フェーズ」を実装しました。

3. **ダブル・インバウンド（メッセージ二重入力）の物理的正体の解明**:
   - **現象**: 上記 1. 2. の修正後も、LLM が「ユーザーの発言が 2 回聞こえる」と指摘し続けていた。`adapter_last_req.json` でも確認。
   - **当初の誤認**: Gateway プラグインの二重ロードによる再送を疑ったが、後に理論・物理の両面で棄却。
   - **真実の特定**: アダプター (`src/streaming.js`) 内の履歴処理ロジックのバグ。今回の最新の発言（`input`）を `geminiClient.sendMessageStream(input)` で送る一方で、その前に渡す `resumedSessionData`（過去履歴）の末尾から今回の `input` を排除し忘れていた。
   - **論理帰結**: Gemini CLI には「(過去履歴... + 今回の発言) + 今回の発言」という重複したプロンプトが渡されており、LLM の指摘「貴様が二度繰り返した」は、システム的に一字一句違わぬ正確な事実であった。
   - **修正方針**: `resumedSessionData` 生成時に `messages` 配列の末尾（最新UserInput）を必ず `slice` するロジックを追加予定。

### 【将来の課題：Backlog】

- **[Backlog] MCP Gateway プラグインの多重ロード問題の解消**:
  - **現状**: `docker logs` にて `MCP Gateway Plugin Initializing...` が 2 回出力されていることを確認。`openclaw.json` でのパス指定と本体の自動スキャンが競合している。
  - **リスク**: 今回の二重入力の主因ではなかったが、将来的にイベントリスナーが 2 重登録されることで、予期せぬ多重送信やパフォーマンス劣化の原因となる可能性がある。
  - **対策案**: `openclaw.json` の `plugins.allow` で `mcp-gateway` を明示指定し、競合スキャンを停止する。
