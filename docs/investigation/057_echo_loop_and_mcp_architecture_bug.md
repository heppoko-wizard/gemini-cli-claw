### 調査レポート：[LLMメッセージ重複・無限ループ（エコー）問題の根本原因調査]

- **仮説**: Docker コンテナ内部にて LLM がメッセージを二重・三重に重複送信し、場合によっては無限ループを引き起こす原因は、LLM 自身の「自己暗示（Degenerate Repetition）」によるものであると考えた。

1. **Persistent Runner (常駐プロセス) の状態リーク**:
   - `git diff` および `src/runner.mjs` のコード現状を確認した結果、2026-03-20 に導入された `RunnerPool` アーキテクチャにより、1つの Node.js プロセス内で `config` や `geminiClient` のインスタンスがリクエストを跨いで再利用（ステートフル化）されている事実を確認しました。
   - **対策済**: `runner.mjs` にて `prompt_id` に基いたエフェメラルなセッションIDを強制付与することで、歴史の自己増殖を物理的に遮断しました。

2. **イベントリスナーのメモリリークの副次的発見**:
   - `src/streaming.js` の `runGeminiStreaming` 内において、リスナーが破棄（`removeListener`）されておらず、N個分のログ出力が行われるバグを特定しました。
   - **対策済**: ストリーミング終了時に明示的に `removeListener` を行うクリーンアップを実装しました。

3. **ダブル・インバウンド（メッセージ二重入力）の物理的正体の解明**:
   - **現象**: 上記 1. 2. の修正後も、LLM が「ユーザーの発言が 2 回聞こえる」と指摘し続けていた。`adapter_last_req.json` でも確認。
   - **当初の誤認**: Gateway プラグインの二重ロードによる再送を疑ったが、後に理論・物理の両面で棄却。
   - **真実の特定**: アダプター (`src/streaming.js`) 内の履歴処理ロジックのバグ。今回の最新の発言（`input`）を `geminiClient.sendMessageStream(input)` で送る一方で、その前に渡す `resumedSessionData`（過去履歴）の末尾から今回の `input` を排除し忘れていた。
   - **論理帰結**: Gemini CLI には「(過去履歴... + 今回の発言) + 今回の発言」という重複したプロンプトが渡されており、LLM の指摘「貴様が二度繰り返した」は、システム的に一字一句違わぬ正確な事実であった。
   - **修正方針**: `resumedSessionData` 生成時に `messages` 配列の末尾（最新UserInput）を必ず `slice` するロジックを追加予定。
   - **事実の特定**: アダプター (`src/streaming.js`) において、最新の入力を「履歴の末尾」と「今回の入力」の 2 回、不必要に Gemini に渡していた設計バグを特定。
   - **対策済**: `resumedSessionData` 生成時に最新の UserInput を `slice` で除外するロジックを実装し、二重送信を根絶。

4. **「アシスタント発言の二重生成・予言」現象の解明と浄化**:
   - **事実の特定**: `adapter_last_req.json` の解析により、修正「前」に生成された古い履歴データ自体が物理的に二重化・順序逆転して保存されていた事実を確認。
   - **結論**: 現在のシステムは清浄だが、Gateway が保持する「汚染された過去履歴」の残像（After-Image）が引き継がれたことによる一過性の現象である。新規セッションにおいては物理的に一度しか送出されていないことを確認済み。

5. **システムログ（ハートビート・クーロン）の送信経路調査**:
   - **事実の確認**: ハートビート等の内部ログはチャット履歴（`messages` 配列）には一切インジェクトされず、Gemini 側からは不可視であることを物理的に確定。

### 【追記：2026-03-21 無限エコーループの再発と真の本質（Geminiモデルの退化的反復と履歴汚染）】

#### 1. 現象の再発とログからの事実確認
- **ユーザー報告**: 修正後も「10回以上のループが起こる」「強制停止しない限り止まらない」「法則性が見えない」「OpenClawからの送信は1度のみ」との報告。
- **ログの事実確認** (`logs/adapter_last_req.json`): 履歴上に、アシスタントの全く同じテキストが `⚙️ tooluse[...]` マーカーを挟んで物理的に二重・三重に記録されている事象（物理的重複）を確認。

#### 2. 原因の仮説修正と特定（システムバグからモデル挙動へ）
- **誤認の訂正**: 当初疑われた `streaming.js` 内の SSE ストリーム（`messageHandler`）のリスナーリークは存在せず、適切に `removeListener` されていることをコード上で確認。プロセス再利用時の `stdout/stderr` のリークは事実として存在するが、これは `adapter.log` の重複を招くだけであり、UIへの多重送信の直接原因ではない。
- **真の根本原因**: Gemini CLI の YOLO モード（承認不要のツール自動実行ループ）において、Gemini モデル自身がツール実行の前後で**全く同じテキストを再生成（退化的反復: Degenerate Repetition）している**事実を特定。確率的なテキスト生成であるため、法則性がない（1回で終わることもあれば10回以上繰り返すこともある）。

#### 3. 無限ループへの増幅メカニズム（死のスパイラル）
1. Gemini モデルが自発的に同じテキストを複数回出力する。
2. OpenClaw 側はそれをそのまま「1つの長いアシスタントメッセージ」として履歴に保存（履歴汚染）。
3. 次の会話ターンで、OpenClaw はこの「重複した履歴」を抽出してアダプター経由で Gemini CLI へ送信。
4. Gemini モデルは In-context Learning により「前回このように繰り返して答えた」という自己暗示的文脈を学習し、さらに重複を加速・増幅させる。

#### 4. 抑止機構の欠落
- OpenClaw からは `max_completion_tokens: 8192` 等が指定されているが、アダプターは現在この上限値を Gemini CLI に伝播させていない。そのため、CLI側はデフォルトの大きな上限値で動作し、ループを早期に断ち切れない一因となっている。

#### 5. 調査の総括
現在のシステムコード（Node.js アダプター）には「UIへメッセージを物理的に多重送信する」バグは存在しない（1度しか送っていないというユーザーの観測と一致）。
真の問題は、**Gemini モデルの推論時の確率的な反復挙動が、ステートレスな履歴同期アーキテクチャによって「正解の文脈」として永続化・再入力され、指数関数的に増幅されるフィードバックループ**にあると断定する。現状の仕組み（Gemini CLI への完全委譲）では、モデルの気まぐれによる暴走をアダプターレイヤーのみで完全に制御することは困難（原因不明・不可抗力）である。

#### 6. 現状のステータス：小康状態（2026-03-21 21:20）

- **結論**: システム的な物理バグ（二重送信ロジック等）ではなく、モデルの気まぐれに起因する確率的な事象であることが裏付けられた。現在は安定して動作しており、「小康状態」と判断。

# 調査報告：057 - エコーループおよび MCP アダプター履歴崩壊の根絶

## 1. 概要
OpenClaw と Gemini CLI Adapter 間で発生していた以下の深刻な不具合を物理的に特定し、解決しました。
1. **エコーループ (Echo Loop)**: モデルが自分の過去の発言を繰り返す、あるいは二重に処理する現象。
2. **ツール結果消失 (Null Result)**: ツールは実行されているが、履歴復元時に結果が空になり、モデルがハルシネーションを起こす現象。
3. **Gemini 400 エラー**: セッション再開時に API が INVALID_ARGUMENT エラーを返す現象。

## 2. 原因分析 (Root Causes)

### A. エコーループの真因：セッション状態の残留
- **事実**: `runner.mjs` が常駐プロセスとして再利用される際、Gemini CLI の `Conversation` インスタンスに過去のメッセージが蓄積されたままになっていた。
- **解決**: リクエストごとに `ephemeralSessionId` を生成・付与し、物理的にセッションを隔離した。

### B. ツール結果消失の真因：標準出力捕捉の漏れ
- **事実**: Adapter 側で `mcp.callTool` イベントのみを待機しており、Gemini CLI がツール結果を `stdout` (JSON行) 経由で出力するケースを無視していた。
- **解決**: `streaming.js` に `stdout` パースロジックを実装し、JSON 行をインターセプトして `tool_result` を捕捉・永続化するようにした。

### C. 400 エラーの真因：履歴ターンの不整合
- **事実**: 歴史を復元する際、`model (tool_calls)` を含むメッセージの直後に `function (responses)` ターンを配置せず、一つのメッセージに封じ込めていたため、Gemini API の「ターン制約（呼出と応答は対であること）」に抵触した。
- **解決**: `streaming.js` の履歴再構成ロジックを修正。ツールマーカーを検知した時点で、メッセージを `model (calls)` ターンと `function (responses)` ターンの 2 つに物理的に分割して Gemin に送るようにした。

## 3. 適用した修正ファイル
1. [src/streaming.js](file:///home/heppo/DEV/openclaw-gemini-cli-adapter/src/streaming.js): 履歴の再構成（2ターン分割）および stdout からのツール結果捕捉ロジック。
2. [src/runner.mjs](file:///home/heppo/DEV/openclaw-gemini-cli-adapter/src/runner.mjs): セッション隔離 (`ephemeralSessionId`) の実装。

## 4. 残された課題と提言
- **出力の重複（稀発）**: 履歴の分割により、稀にモデルが「語り出し」を繰り返す現象が観測された。これは履歴内の `model` ターンのテキストが空であることに対するモデルの反応である可能性がある。
- **安定性**: 物理的なファイル永続化 (`logs/contexts/default/`) に頼っているため、ディスク I/O の競合に注意。
