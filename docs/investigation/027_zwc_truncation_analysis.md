# 調査レポート：ZWC 文字数制限によるデータ欠損とパースエラーの特定

## 1. 調査の目的
`zwc_errors.log` における `INVALID ZWC ERROR` の発生原因を特定し、データ欠損がなぜ起きるのかを解明する。

## 2. 調査結果

### 2.1 現象の事実確認
- **ログの分析**: `zwc_errors.log` には `Bad control character in string literal` が記録されており、デコード後の JSON が `{"timestamp":"2026-03-15...` のように途中で途切れていることが確認された。
- **Raw データの断片化**: ZWC の終了コード（`ZWC_END`）が含まれていないケースが多数あり、物理的な「切り詰め」が発生していることが確定した。

### 2.2 根本原因の特定
- **OpenClaw Gateway の制約**: `src/gateway/server-methods/chat.ts` を調査した結果、恒久的な定数 **`CHAT_HISTORY_TEXT_MAX_CHARS = 12,000`** を発見。
- **データ膨張のメカニズム**: ZWC は見えない文字であるが、1文字としてカウントされる。SSoT 3.1 までの方式では、バイナリデータを ZWC エンコードする際にデータ量が **約 9 倍** に膨張（1バイト -> 9文字）するため、少し長い会話履歴を送るだけで 12,000 文字の閾値を容易に超えていた。
- **切り詰めの発生**: 制限を超えた分は `...(truncated)...` という文字列に置換され、以降の ZWC データは永久に失われる。これにより JSON 構造が破壊され、パースエラーを引き起こしていた。

## 3. 解決策（SSoT 4.2 の導入）
ポインタ JSON を ZWC で隠蔽するのをやめ、等倍のデータ量で済む **プレーンテキスト・ポインタ** 形式へ移行した。

- **データ削減**: 膨張率を 9:1 から **1:1** へ低減。
- **視認性の向上**: `>   ⚙️ Using tool [name] [id:...] ...` のようにブロッククォート形式で ID を直接表示。
- **安全性**: 履歴を LLM に送り返す直前に、アダプターが付与したこれら表示行（ID を含む）を正規表現で **全消去（Total Cleansing）** し、LLM の模倣を防止。

## 4. 結論
本調査により、通信エラーの真因が「Adapter のバグ」ではなく「Gateway 側の物理的制限」であることが判明した。SSoT 4.2 のプレーンテキスト化により、データ量は劇的に削減され、この制限内での安定運用が確保された。
