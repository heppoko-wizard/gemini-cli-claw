### 調査レポート：メモリ最適化監査（低スペックマシン対応）

【調査の道筋（仮説と検証のトレイル）】
- **Phase 1: 調査計画**
    - **現状の把握**: OOM 障害（DEBUG=true 関連）は解決したが、ユーザーよりさらなるメモリ消費の削減と低スペックマシン対応の要望があった。
    - **調査の仮設**:
        1. 実行パスにデバッグ用の不要な `console.log` や巨大オブジェクトの文字列化が残っている。
        2. `server.js` 等でリクエスト履歴やセッションデータが過剰にメモリ内に蓄積されている。
        3. メディアファイルの処理において、ストリームではなくメモリバッファへの全ロードが行われている。
        4. `runner-pool.js` のプロセス管理において、不要なリソース保持が発生している。
    - **調査の手順**: (完了)
        1. `grep_search` により `console.log`, `console.error`, `JSON.stringify` の使用箇所を抽出・評価。
        2. `server.js` および `session.js` におけるメモリ保持ロジック（キャッシュ等）の監査。
        3. メディア処理 (`src/media.js`) のメモリ効率確認。
        4. `runner-pool.js` の IPC 通信とプロセスライフサイクルの再点検。

- **事実の発見1: `src/server.js` での過剰かつ同期的なリクエスト保存**
    - `src/server.js:121` にて、すべてのリクエストを `raw_req.bin` に同期的に書き出している。
    - `src/server.js:180` にて、パース後の `body` を `JSON.stringify(body, null, 2)` で文字列化し、`adapter_last_req.json` に同期的に書き出している。
    - **問題点**: 画像などの巨大なリクエストが含まれる場合、メモリ上でデータが複数回複製され（Raw Buffer -> String -> JSON Object -> Formatted String）、さらに同期的なファイル書き込みによってイベントループが停止する。これは低スペックマシンにおける応答性能低下と OOM の直接的な原因となる。

- **事実の発見2: `src/streaming.js` でのメモリ内キャッシュの無限肥大化**
    - `src/streaming.js:17` で定義されている `toolMemoryStore` (Map) に、セッションごとのツール実行結果が蓄積されるが、**削除や期限切れ（TTL）のロジックが一切存在しない**。
    - **問題点**: 長期間アダプターを稼働させると、これまでに使用されたすべてのツールの結果がメモリに残り続け、リークの原因となる。

- **事実の発見3: `src/runner.mjs` での性能計測ログのオーバーヘッド**
    - `src/runner.mjs` 内に `[Runner:perf]` というプレフィックスの `console.error` が多数散布されている。
    - **問題点**: 単独では軽微だが、大量のイベント処理中には文字列生成と I/O 発行が CPU リソースを圧迫し、全体的な処理の「余分な重さ」を生んでいる。

【コードベース・仕様から確認された最終的な事実】
- リクエストのデバッグ保存（`raw_req.bin`, `adapter_last_req.json`）は、**現在の実装では条件なし（常に有効）**となっており、本番稼働において無駄な負荷となっている。
- ツールコンテキストの Map 管理には、履歴の長さに応じたメモリ消費の増大を抑える仕組みがない。

### 【Phase 1.5: アーキテクト視点での自己懐疑と再検証】

ユーザーの指摘を受け、「削ってはならないものを削るリスク」がないか、コードベースの依存関係を再点検しました。

- **自己懐疑1**: `raw_req.bin` 等を保存しない設定にして、他の処理（例えば画像解析など）が壊れないか？
    - **再検証結果 (安全)**: `grep_search` による全ファイル検索の結果、これらのデバッグファイルは `server.js` 内で書き込まれるのみで、**他のいかなるモジュールからも読み込まれていない**（Read されていない）ことが確定しました。したがって出力停止による副作用はゼロです。
- **自己懐疑2**: `toolMemoryStore` (Map) をパージ（削除）した場合、過去のツール実行結果（リハイドレート）が欠損してエラーにならないか？
    - **再検証結果 (安全)**: `src/streaming.js` の `loadToolContext` 関数を確認したところ、メモリ内キャッシュ（Map）に見つからない場合は、自動的に `fs.readFileSync` によってディスク（`/app/logs/contexts/...`）から読み込む **フォールバック機構が既に実装されている** ことが判明しました。つまり、主記憶の Map は純粋なパフォーマンス向上キャッシュであり、**強制的に消去しても動作は全く破壊されません**。LRU（Least Recently Used）キャッシュの導入が極めて安全かつ適性です。
- **自己懐疑3**: パフォーマンス計測ログ (`[Runner:perf]`) の抑制は本当に最適化になるか？
    - **再検証結果 (安全かつ有効)**: Runnerプロセスで `console.error` が発火すると、親プロセス（`runner-pool.js`）が `runner.stderr.on('data')` で文字列として受信し、さらにメインコンソールへ出力します。つまり、ログの数だけ **IPC を跨いだ文字列シリアライズとコンテキストスイッチが発生** しています。不要なログの発火を元から断つことは、低スペック環境において明確な最適化（CPU負荷低減）となります。

上記により、最初の最適化案はすべて「非破壊的かつ安全」であることが証明されました。

---
### 最適化案（Phase 3 への提案）

1.  **環境変数によるデバッグ出力の制御**: 
    - `ADAPTER_DEBUG=true` の場合のみ、リクエストのファイル保存や性能計測ログを有効にする。デフォルトは `false` とし、リソース消費を最小化する。
2.  **キャッシュパージ（掃除）の実装**:
    - `toolMemoryStore` について、一定サイズ以上の保持を防ぐ簡易的な LRU（またはサイズ制約付き）キャッシュへ移行する。ディスクフォールバックがあるため安全。
3.  **巨大リクエストの文字列化回避**:
    - デバッグ無効時は、`Buffer.toString()` などの不要な文字列コピーを削減する。
