### 調査レポート：ウォームアップの徹底 vs. 常駐化 vs. MCP独立化 の比較

【調査の道筋（仮説と検証のトレイル）】
- **仮説1**: 使い捨て（Disposable）のままでも、ウォームアップ段階で MCP 起動 (10秒) を完了させれば高速化できるのではないか？
- **検証1**: `runner.mjs` を改造し、`ready` を送る前にダミーのツール呼び出し等で MCP を強制起動させることは技術的に可能。
- **事実の発見1**: しかし、この方式は「1人の客が来たら店（プロセス）を壊して、次の店を 10 秒かけて建てる」行為を繰り返すことになる。**秒間リクエストが多い場合、スタンバイが枯渇して結局 10 秒待たされる**（スループットの限界）。また、常に重い MCP 起動がバックグラウンドで走り続けるため、CPU/メモリへの負荷が高い。

- **仮説2**: MCP サーバーをランナーから切り離して独立（Standalone）にできるか？
- **検証2**: MCP は本来サーバー（SSEやstdio）として動く設計のため、独立は可能。
- **事実の発見2**: しかし、現在の `gemini-cli` は「自身が MCP クライアントとして子プロセス（stdio）を管理する」設計に最適化されている。MCP を独立させるには、アダプター側に「常駐型 MCP プロキシ」を新設し、ランナーがそこに接続する仕組みが必要となり、開発コストが非常に高い。

- **仮説3**: 「常駐型ランナー（Persistent Runner）」は、ユーザーの言う「MCP の独立」と何が違うのか？
- **事実の発見3**: 実は、**「常駐型ランナー」こそが、ユーザー様の仰る「エンジンの独立化」の最もシンプルかつ確実な実装形態である。**
    - ランナーを殺さない ＝ 内部で保持している MCP 接続も死なない。
    - つまり、ランナーそのものが「常駐型 MCP クライアント」として機能し続ける。

【最終的な比較表】

| 項目 | A. 現状（簡易ウォームアップ） | B. 徹底ウォームアップ (使い捨て) | C. 常駐化 (Persistent) ※推奨 |
| :--- | :--- | :--- | :--- |
| **方式** | Node起動だけ先にやる | MCP起動まで先にやって待機 | プロセスを捨てずに使い回す |
| **TTFT (1回目)** | 13秒 (MCP起動を待つ) | **3秒 (即応)** | **3秒 (即応)** |
| **TTFT (連続時)** | 13秒 (毎回発生) | 13秒 (補充待ちが発生) | **3秒 (常に高速)** |
| **リソース負荷** | 低 | **極めて高い (常に10sの起動が走る)** | 低 (1回起動したら維持のみ) |
| **状態の清潔さ** | 最高 (毎回リセット) | 最高 (毎回リセット) | 中 (明示的なリセットが必要) |

---
※ 結論：使い捨てを維持したまま 10 秒の初期化を「隠す」ことは可能ですが、連続リクエストに弱く、サーバー負荷が激増します。「常駐化」は、ユーザー様が提案された「MCPの独立」という思想を、最も効率的に実現する手段です。
