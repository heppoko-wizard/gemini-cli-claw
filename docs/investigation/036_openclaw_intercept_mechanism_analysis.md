# 調査レポート：OpenClaw インターセプト問題の深層分析 (Fact Finding Report)

## 1. 調査目的
「なぜ OpenClaw が、Gemini CLI が既に管理・実行しているツールを横取りしようとするのか」という根本的な動作原理（インターセプト・メカニズム）を明らかにする。

---

## 2. インターセプト発生のメカニズム (The Intercept Mechanism)

### 2-1. OpenAI 規格における「実行権」の移動
OpenAI の `chat/completions` プロトコルでは、モデルが `tool_calls`（実行依頼）を返した時点で、一度**ストリームを完結させる（`finish_reason: "tool_calls"`）**のが一般的である。
このタイミングで、クライアント（OpenClaw Gateway）は「実行権が自分に戻ってきた」と判断し、メッセージ配列に含まれる `tool_calls` を自身のスキルエンジン（`tool_calling`）で実行しようとする。

### 2-2. Adapter が引き起こしている「偽の終了」
現在の `streaming.js` および Gemini CLI の動作においては以下の不整合がある：

1.  **非自律的な終端**: Gemini CLI が内部でツールを実行し、次のターンの推論に進もうとしている間、Adapter は OpenClaw に対して「まだ回答中である（`finish_reason: null`）」と伝え続ける必要がある。
2.  **死の谷 (Dead Valley)**: もし `total_calls` を送った直後に Adapter が Gemini CLI の自律ループを待たずに SSE を一度「完結」させてしまうと、OpenClaw はそれを「自分への丸投げ」と受け取ってしまう。

### 2-3. OpenClaw 側の誤解の正体
OpenClaw が `Tool not found` と叫ぶのは、以下の理由による：
- **事実**: アダプターが返した `tool_calls` の関数名（例: `read_file`）は、Gemini CLI 内部のツールセットには存在するが、**OpenClaw Gateway 側が認識しているツールセットには存在しない**。
- **誤解**: OpenClaw は、そのツール呼び出しが「アダプターの先で完結するプロセスの一部」であると知らないため、自分に登録されたスキル（`fetch`, `serp` 等）の中から探してしまい、見つからずにエラーを出す。

---

## 3. 【結論】なぜ誤解釈が起きていたか

> ツール実行”結果”としてgeminicliが送ってきた情報をopenclawが誤解釈してopenclaw側で実行しようとしてるんだ？

**回答：実行権の「境界線」を明確に示せていなかったことが原因です。**
- OpenClaw 側から見れば、アダプターから `tool_calls` が送られてきたら「（OpenAIの仕様通り）自分が実行して結果を返すべきタスク」だと盲信してしまいます。
- 私たちが SSoT 5.1 でやったことは、「ツール情報をリーズニング（ただの独り言）に隠す」ことで OpenClaw を煙に巻き、実行権を渡さないようにすることでした。
- しかし、これは**「履歴の破壊」**という別の代償を払いました。

---

## 4. 教訓と解決策
OpenClaw に「これはお前の仕事ではない（既に中での処理が決まっている）」と正しく伝えるには、テキストに隠すのではなく、通信プロトコル上の**「状態管理」**で制御すべきでした。

- **解決策**: SSE ストリームを維持したまま、Gemini CLI の `tool_result` を待ち、それを `role: "tool"` として「自ら消費して次の回答へ繋げる」姿を OpenClaw に見せ続ける（ストリームを一度も止めない）設計が必要です。

---

## 5. [再評価] 030 レポートの一次調査事実との照合 (Self-Audit)

### 5-1. 一次情報の確認
`030_openclaw_thought_tool_spec.md` には、以下の一次調査（コンテナ内 dist コードの grep）に基づく確認済みの事実が記録されている。

- **事実A（確認済）**: OpenClaw Gateway は `tool_calls` を受信すると、自身のスキルエンジンでそのツールを実行しようとする仕様である。
- **事実B（確認済）**: `google_web_search` 等の Gemini CLI 内部ツールは OpenClaw には未登録のため、`Tool not found` エラーとなる。
- **事実C（確認済）**: `finish_reason` の値に関わらず（`null` であっても）、`tool_calls` が SSE チャンクに含まれていると、OpenClaw はインターセプトを試みる。

### 5-2. 036 レポートの主張との照合

| 036 の主張 | 事実との整合性 | 評価 |
|---|---|---|
| 「`finish_reason` の制御で解決できる」 | **不正確。** `finish_reason: null` のまま `tool_calls` を送っても、030 の事実C によりインターセプトは発生する。 | ❌ 誤記：修正が必要 |
| 「OpenClaw がツールを自分のものと誤解する」 | 正確。030 の事実AおよびBで確認済み。 | ✅ 正確 |
| 「実行権の境界線が不明確」 | 正確。030 の「矛盾の特定」と合致。 | ✅ 正確 |
| 「ストリームを終わらせなければ解決する」 | **不正確。** `tool_calls` の存在自体がトリガーであり、ストリームの維持だけでは防げない。 | ❌ 誤記：修正が必要 |

### 5-3. 結論の修正（追記）
**【修正された結論】** インターセプトの回避策における唯一の確実な方法は「`tool_calls` フィールドを OpenClaw に送らないこと」である。これは `030` の SSoT 5.1 の結論（`reasoning_content` へのリダイレクト）と一致する。

`finish_reason` の制御は補助的な効果があるかもしれないが、「根本的な解決策」ではない。`tool_calls` 送出の廃止あるいは、`tool_calls` を OpenClaw にとって意味不明（実行不能）な形で渡す変換レイヤを設けることが本質的な解決策である。

## 6. [深層分析] 二重ループ衝突（Double Loop Conflict）の実態

ユーザーの鋭い指摘に基づき、OpenClaw の内部ループと Gemini CLI の自律ループが衝突した際に何が起きていたのかを詳細に分析した。

### 6-1. 衝突のタイムライン（Crossing the Streams）

1.  **ターンの開始**: ユーザーの依頼を受け、OpenClaw が Adapter に POST リクエストを送信。
2.  **Gemini 内部ループの始動**: Adapter が Gemini CLI を起動。Gemini は自律的に思考し、ツール（例: `read_file`）の実行を決定する。
3.  **インターセプトのトリガー（SSoT 5.1以前）**: Adapter が `delta.tool_calls`（OpenAI正規規格）を送出。
4.  **OpenClaw の「所有権奪取」**: OpenClaw はこの信号を受け取ると、「自分のターンだ」と誤解する。
    - **動作 A**: OpenClaw は現在のストリームの残りを**無視（読み捨て）**し始める。
    - **動作 B**: OpenClaw は自身のエンジンで `read_file` を実行しようとするが、失敗（Not Found）。
5.  **幽霊プロセスの発生**: 一方その頃、Gemini CLI は**内部で既に `read_file` を実行完了**しており、次の回答チャンクを生成し続けている。しかし、Adapter が返している SSE ストリームは、4.-A により OpenClaw 側ですでに「切断」または「無視」されている。
6.  **二重送信・無限ループの予兆**: もし OpenClaw が（失敗したとはいえ）ツール結果を無理やり捏造して次ターンのリクエストを Adapter に送った場合、Gemini CLI は「自分が今まさに完了したはずのツール実行」について、外部（OpenClaw）から「全く別の（あるいは失敗した）結果」を突きつけられることになり、文脈が決定的に崩壊する。

### 6-2. 具体的に起こったこと（カオスの中身）
- **エラーの早期噴出**: OpenClaw 側で `Tool not found` が出ると、OpenClaw のループ自体がエラーで停止するため、幸いにも「無限の再リクエスト」に陥る前にクラッシュ（停止）していた。
- **無意味なリソース消費**: Gemini CLI は裏で回答を完結させようと必死に動き続けているが、その出力は誰にも届かず、虚空に消えていた。
- **解決策としての SSoT 5.1（リーズニング逃避）の功罪**:
    - **功**: ツール情報を `reasoning_content`（テキスト）として送ることで、OpenClaw の「所有権奪取（インターセプト）」を完全に無効化し、Gemini CLI の自律ループを完走させた。
    - **罪**: 本来構造化データであるべきツールログを「地の文」に変えたことで、次ターンの履歴リクエストにおいて Gemini 自身が「自分の過去の行動を理解できない」という**履歴汚染**を引き起こした。

### 6-3. 結論：目指すべき姿（SSoT 6.0）
OpenClaw のループ（外側の輪）を完全に沈黙させつつ、Gemini CLI のループ（内側の輪）が生成した「確定した歴史（ツール実行記録）」を、**一度も汚染されることなく正規形式のまま**、次のターンまで受け渡す「カプセル化された履歴管理」が必要です。

## 最終的な結論
本調査により明らかになったインターセプト・メカニズム（`tool_calls` フィールドへの自動反応）を回避するため、**SSoT 6.0（ツールマーカー ID 方式）**が採用されました。

- **対応ステータス**: 完了 (Completed)
- **解決の鍵**: `tool_calls` フィールドの送出を完全に廃止し、マーカー ID による本文内での情報伝達と、アダプター側での履歴復元（リハイドレーション）を組み合わせることで、境界線の問題を解消しました。
