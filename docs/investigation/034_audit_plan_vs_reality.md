# 自己監査レポート：計画と実装の重大な乖離 (Self-Audit Report)

## 1. 調査目的
過去の SSoT 5.0/5.1 の計画に対し、現在の実装がどう「約束を破っているか」を明らかにする。

---

## 2. 計画時の約束 (Audit Findings)

### 2-1. SSoT 5.0 計画 (docs/plans/029/implementation_plan.md)
以下の 2 点が明確に定義されていた。
1.  **「OpenAI互換 tool_calls の正規利用」**: ツール情報を `delta.tool_calls` フォーマットで返し、OpenClaw の履歴管理に委ねる。
2.  **「履歴復元ロジックの委任」**: `streaming.js` の履歴復元を `converter.js` に任せ、正規の構造として再構築する。

### 2-2. 実際の変節：SSoT 5.1 の導入
実装中に、OpenClaw Gateway が `tool_calls` を受け取ると「自身のスキルエンジンで実行しようとしてエラー（Not Found）を吐く」という挙動（インターセプト）に遭遇した。

これを回避するため、我々は以下の「その場しのぎ」の修正を行った：
- **変更**: `delta.tool_calls` をやめ、`delta.reasoning_content` に「人間向けの装飾テキスト（⚙️ 等）」として流す。
- **正当化**: 「これにより OpenClaw の奪取を回避し、Gemini CLI の自律性を守る」と説明。

---

## 3. 約束違反と負債の発生

### 3-1. 履歴復元プロセスの「沈黙の破壊」
計画では `tool_calls` オブジェクトから履歴を復元するはずだった。しかし、`reasoning_content` に「ただのテキスト」として逃げたことで、以下の事態を招いた：
1.  **構造化データの喪失**: ツール名や引数が「地の文」として送られ、OpenClaw に記録された。
2.  **復元ロジックの形骸化**: `streaming.js` には以前の ZWC 方式や OpenAI 互換方式の残骸（L140-156）があるが、それらは「オブジェクト」を期待している。実際のリクエストには「⚙️ が付いたテキスト」として戻ってくるため、これらのロジックは一切発動せず、**ただの会話として Gemini に受け渡された。**

### 3-2. 結論：計画は存在したが、実装が思想に追いついていない
> 「過去の実装計画にそのように実装するように書いてありましたか？」

**回答：いいえ。むしろ「正規の形式で送受信し、履歴を汚染しない」ことが本来の計画でした。**

しかし、OpenClaw のインターセプトという壁に対し、我々は「データをテキスト（装飾）に格下げする」という安易な回避策（SSoT 5.1）を選び、同時に「その格下げされたデータを元に戻す（逆パース）」という責任を放棄しました。これが今回の「履歴にツールが登場し、LLM が困惑する」という不具合の正体です。

---

## 4. 教訓
- **データの「格下げ（正規構造→テキスト）」は常に毒である**: 一度テキストに混ぜた情報を、後のターンで再び構造化データとして取り出す（リハイドレーション）のは困難であり、今回のような「履歴汚染」という形で必ずしっぺ返しが来る。
- **SSoT 5.1 は不完全な設計だった**: OpenClaw を騙すためにテキスト化したのであれば、受け取り側でその嘘を解いて元の型（Thought/ToolCall）に戻して Gemini に渡すべきだった。

---
## 結論
本監査で見つかった「プランと現実の解離」は、**SSoT 6.0（ツールマーカー ID 方式）**の導入により解消されました。インターセプトを回避しつつ、正規の履歴を保持する最終的なアーキテクチャが確立されました。

- **解決策の詳細**: `035_ssot_6_architecture_design.md` を参照。
