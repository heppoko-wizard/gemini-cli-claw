# 調査報告：Docker ビルドの最適化とリソース管理の改善

## 1. 課題：ビルドの低速化とメモリ不足
最適化前の Docker 環境では、以下の問題が発生していた：
- **ビルドコンテキストの肥大化**: `.dockerignore` が不十分で、ホスト上の `node_modules` や巨大なログファイルが毎回 Docker デーモンに転送されていた。
- **冗長な依存関係**: `npm ci` が `node-pty` 等の重量級かつ不要なオプションパッケージのコンパイルを試み、低リソース環境でのビルド時間を 20 分以上に増大させていた。
- **イメージサイズ**: 開発用ツールが最終イメージに残っており、1GB 近くに達していた。
- **不安定なランタイム**: メモリ不足時にコンテナがホストを巻き込んでクラッシュするリスクがあった。

## 2. 実効策

### 2-1. マルチステージビルドによる隔離
`build` ステージで `build-essential` 等を用いてネイティブモジュールのリンクを行い、`runtime` ステージ（`node:24-bookworm-slim`）へ成果物（`node_modules`）のみをコピーする構成に変更した。これにより、ランタイム環境から数百MBのビルドツールを排除した。

### 2-2. 不要なランタイム (Bun) の削除
Persistent Runner の導入により、Bun による「プロセスの高速起動」の利点が相対的に低下した（一度起動すれば再利用されるため）。メモリ管理の安定性とイメージの単純化を優先し、Node.js に一本化した。

### 2-3. `npm ci --omit=optional` の導入
これがビルド時間短縮に最も寄与した。アダプターの動作に必須ではない `node-pty` 等のコンパイルを回避することで、ビルド時間を 90% 以上削減した。

### 2-4. コンテナのリソース制限 (docker-compose.yml)
ホストのメモリを保護するため、以下の制限を導入：
- `limits.memory: 2G`
- `reservations.memory: 512M`

## 3. 結果の比較

| 項目 | 最適化前 | 最適化後 | 効果 |
| :--- | :--- | :--- | :--- |
| ビルド時間 | 20分超 (Time out) | **約2分14秒** | **~90% 削減** |
| イメージサイズ | 約940 MB | **約316 MB** | **~66% 削減** |
| ビルドコンテキスト | 数百 MB (推定) | **約26 MB** | 高速転送 |
| 安定性 | メモリ不足で落ちる可能性 | 制限下での安定稼働 | 安全性向上 |

## 4. 結論
今回の最適化により、開発効率（ビルド速度）と運用安定性（メモリ制御）の両面で大幅な改善を達成した。特にマルチステージとオプション依存関係の整理は、低リソース環境での Docker 運用において決定的な差を生むことが実証された。
