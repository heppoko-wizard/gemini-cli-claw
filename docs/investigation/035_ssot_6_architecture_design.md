# SSoT 6.0 アーキテクチャ設計書：正規履歴管理とデバッグ性向上の抜本改革

## 1. 背景と課題 (Background)
SSoT 5.1 において、OpenClaw のツール横取り（インターセプト）を避けるために「ツールログをリーズニング（テキスト）として送る」という回避策を採ったが、これが以下の深刻な問題を招いた。

- **履歴汚染**: リーズニング内のテキスト（⚙️ 等の装飾を含む）が次ターンの履歴リクエストの本文 (`content`) にマージされ、LLM の文脈を破壊する。
- **リーズニングの本来の意味の喪失**: リーズニングはモデルの思考プロセスを格納すべき場所であり、確定した過去の「実行記録（ツールログ）」を混ぜ込む場所ではない。

## 2. SSoT 6.0 核心の設計 (Core Design)

### 2-1. 【回帰】ツール履歴の正規化
- **方針**: アダプター側での意味のない装飾（⚙️ や Markdown 等）を完全に撤廃する。
- **実装**: `streaming.js` の `tool_call_request` ハンドラにおいて、`delta.reasoning_content` への書き込みを廃止し、正規の **`delta.tool_calls`**（OpenAI規格）での送出に戻す。

### 2-2. 【解決】OpenClaw のインターセプト（奪取）回避
正規の `tool_calls` を送りつつ、OpenClaw 側での実行エラーを防ぐための戦略：

1.  **モデル能力の明示**: `/v1/models` のレスポンスにて、モデルが `function_calling` 能力を持つことを明示的に示唆する属性を付与する（OpenClaw のパース基準に合わせる）。
2.  **`finish_reason` の制御**:
    - Gemini CLI が自らツールを実行している間は、SSE チャンクの `finish_reason` を常に `null` または `reasoning` に保つ。
    - アダプター側で Gemini CLI の `tool_result` イベントを待ち、その結果を `role: "tool"` メッセージとして生成、あるいは次の `content` に繋げる。これにより OpenClaw 側が「モデルが止まった（実行依頼だ）」と判断する隙を与えない。

### 2-3. 【安定性】履歴リクエストの強力なクレンジング
- **方針**: Gemini CLI に履歴を渡す際、OpenClaw から届いた `messages` 配列から「非正規なテキスト（装飾ログ）」や「過去のエラー」を確実にパージしてから、Gemini 内部形式にマッピングする。
- **実装**: `src/server.js` に `⚙️` や `💭` などのパターンを一掃する正規表現を実装。

### 2-4. 【透明性】開発者用生データダンプ (Debug Mode)
- **方針**: 「何が起きているか」をブラックボックス化させない。
- **実装**:
    - `logs/` ディレクトリを Docker ホストにマウントできるよう `docker-compose.yml` を修正。
    - 取得した IPC メッセージ（生の `gemini_event`）を `logs/gemini_events.log` にダンプする機能を `streaming.js` に追加（デバッグフラグで制御）。
    - 履歴リクエストの全貌を `logs/adapter_req_history.json` に保存。
