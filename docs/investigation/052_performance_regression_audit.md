# 調査レポート：052 パフォーマンス劣化（応答30秒）の再調査

## Phase 1: 調査計画 (Investigation Planning)

### 現状の把握
- 現象：メッセージの応答時間が約30秒かかっており、以前導入した「永続ランナー（Persistent Runner）」による高速化効果（約10秒の削減）が失われている可能性がある。
- 3月20日 14:05 UTC の実測値：
    - TTFT (Time To First Token): 21.70s
    - Total Duration: 26.22s
- 懸念点：`[Pool] No runners ready. Queuing request...` がログに記録されており、リクエスト時にランナーが準備できていなかった疑い。

### 調査対象
1. `logs/adapter.log`: 各リクエストにおける `[Pool]` の挙動（ランナーの割り当て、再起動の有無）。
2. `src/runner-pool.js`: `readyRunner` が正しく管理され、リリー後に再利用されているか。
3. `src/runner.mjs`: `run_complete` 送信後のプロセスの状態と、次回の `run` メッセージ受信時の挙動。
4. `src/streaming.js`: IPCメッセージの受信速度と SSE 出力のタイミング。

### 調査結果 (Findings) - V2 (再評価済)

#### 1. 永続ランナーにおけるモデル切替の失敗 (Critical)
`src/runner.mjs` ではリクエストごとに `settings.merged.model.name` を更新していますが、Gemini CLI 内部の `config` オブジェクトおよび `geminiClient` は初回呼び出し時（プロセス起動時）にインスタンス化されており、単なる settings オブジェクトの書き換えは無視される構造（`Config` クラス）であることがソースコード調査により判明しました。
- 影響：ユーザーが高速なモデル（`gemini-2.5-flash`等）を指定しても、バックエンドでは**常にデフォルトの `auto-gemini-3`（高負荷なProモデル）** で処理され続けていました。
- 結論：現在リクエストごとに約 20,000 トークンの履歴が転送されています。Flashモデルであればこの分量は約2〜5秒で処理できますが、Proモデルに強制ルーティングされたことで 30〜80秒 という極端な遅延（TTFT）が発生していました。遅延の「真犯人」はこのモデル固定バグです。

#### 2. セッション情報の伝播について
（※前回報告の訂正）`runNonInteractive` API は設計上 `sessionName` パラメータを受け取らず、`resumedSessionData` によって履歴全体を組み立て直す仕様です。Gemini API自体が標準チャットにおいてステートレス（毎ターン全履歴をアップロードする）であるため、毎回の履歴送信自体は正常な挙動でありバグではありません。問題は「その巨大な履歴をどのモデルがさばくか」だけでした。

#### 3. 起動シーケンスの不一致
`rebuild.js` は Gateway (18789) の起動のみを待機しており、アダプター内部の永続ランナー（プロセス立ち上げに約14秒）の完了を待っていない。
- 影響：起動直後の初回リクエストは必ずランナー起動待ちに衝突し、「遅い」と感じさせる原因となっていた。

## Phase 2: 修正方針 (再評価版)

1. **モデル反映の保証 (最重要)**: `src/runner.mjs` において、モデル指定が来た際に `settings.merged` を書き換えるだけでなく、**`config.setModel(model)` を明示的に呼び出し**、Gemini CLI コアに対してモデル変更を通知するよう修正します。
2. **ウェイトの最適化**: 起動後の初回リクエストがランナー準備待ちに巻き込まれないよう、起動シーケンスを改善するか、ユーザーに対するログの可視性を高めます。
