### 調査レポート：JavaScript heap out of memory (OOM) によるランナークラッシュの分析

【調査の道筋（仮説と検証のトレイル）】
- **仮説1**: 会話履歴の蓄積（トークン量）が多くなりすぎて、Node.js のヒープ制限を超えたのではないか。
- **検証1**: `adapter.log` を確認。`FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory` を発見。
- **事実の発見1**: 会話リセット後（2メッセージのみ）の状態でも、ツール呼び出し直後に同様の OOM で SIGABRT クラッシュが発生することを確認。単なる会話履歴の長さだけが原因ではないことが判明。

- **仮説2**: ツール呼び出し時に、特定の巨大なデータが `stderr` に出力され、それを adapter がメモリに溜め込んでいるのではないか。
- **検証2**: ツール呼び出し直前の `adapter.log` を詳細解析。`[MESSAGE_BUS] publish: ...` という巨大な JSON 出力が `stderr` 経由で記録されているのを発見。
- **事実の発見2**: `runner-pool.js` の `stderr` ハンドラーが、前回のコミット `f249501` で「起動後もすべての `stderr` を `console.error` で出力する」ように変更されていた。

【追加の議論と検証ループ】
- **議論/指摘**: ユーザーより「今までこんなことはなかった」「何か重大なエラーが発生しているのではないか」との指摘。
- **新仮説**: `MESSAGE_BUS` の出力はエラーではなく、Gemini CLI の `debugMode` による正常なデバッグ出力ではないか。
- **真の根本原因の特定（再々々検証）**:
  `f249501` における以下の 3 つの変更が「死のコンボ」として機能し、2.2GB 越えの OOM を引き起こしたことを特定：
  1. **`docker-compose.yml` での `DEBUG=true` 有効化**: これにより Gemini CLI の `MESSAGE_BUS` が詳細モードになり、トークン毎や内部状態変化毎に `AgentConfig` や `History` を含む数MB規模の巨大 JSON オブジェクトをイベントとして発火するようになった。
  2. **`runner.mjs` での無差別 IPC 転送**: 追加されたインターセプターが、上記 `MESSAGE_BUS` からの巨大イベントを全て `process.send({ ... event })` で親プロセスへ送ろうとした。Node.js の `process.send` は送信時にオブジェクトを内部的に再シリアライズするため、メモリ上でデータが複製・肥大化し、V8 のヒープ制限を一気に突破した。
  3. **`runner-pool.js` での `stderr` 垂れ流し**: `stderr` に出力される巨大なデバッグログ（`MESSAGE_BUS` 由来）を全て `console.error` で処理しようとしたため、親プロセス側の負荷も増大。

【コードベース・仕様から確認された最終的な事実】
- Gemini CLI (gemini-js) は `debugMode` が有効な場合、通信や状態更新のたびに極めて冗長な内部情報をイベントとして生成する。
- 以前（`f249501` 前）はこれらを IPC で転送していなかったか、あるいは `DEBUG=true` でなかったため、メモリ消費は安定していた。
- **履歴調査による事実（過去の安定版との比較）**:
  コミット `1ef0da4` を調査した結果、当時の `runner.mjs` にはインターセプターが存在せず、`streaming.js` 側で `stdout` を `JSON.parse` する方式でストリーミングを実現していたことを確認。
  一方、現在の `streaming.js` は IPC メッセージ（`gemini_event`）に完全に依存しており、`stdout` はパースせずログ出力のみを行う構造になっている。

- **リスクの特定**:
  指示通り `runner.mjs` のインターセプターを単純にコメントアウトした場合、アダプター（親）は LLM からの出力を一切検知できなくなり、ストリーミングおよびツール実行が完全に停止する。

【コードベース・仕様から確認された最終的な事実】
- Gemini CLI (gemini-js) は `debugMode` が有効な場合、通信や状態更新のたびに極めて冗長な内部情報をイベントとして生成する。
- 以前（`f249501` 前）はこれらを IPC で転送していなかったか、あるいは `DEBUG=true` でなかったため、メモリ消費は安定していた。
- **根本解決策（修正案）**:
  1. `DEBUG=true` を `false` に戻す（確実なイベント量削減）。
  2. `runner.mjs` のインターセプターをコメントアウトする（ユーザー指示）。
  3. **[必須]** `streaming.js` を `da1f1fe` 以前の「`stdout` パース方式」に差し戻し、IPC に依存しないストリーミングを復元する。
  4. メモリ増設（4GB）は、安全マージンとして残す。

---
※ 本レポートは事実の列挙です。再発防止として、`debugMode` の明示的な無効化についても検討を推奨します。

### 【最終実装：防御的プロパティ抽出 (Pick) による決定的な回避】
当初、「インターセプターのコメントアウト」や「`streaming.js` の先祖返り」を検討しましたが、ストリーミング機能（特に思考プロセスの分離表示）の維持を優先し、以下の**「Pick 型インターセプター」**を最終実装として採用しました。

1.  **`DEBUG=false` への復帰 (`docker-compose.yml`)**: `MESSAGE_BUS` による巨大な内部デバッグイベントの生成自体を停止しました。
2.  **プロパティ抽出 (Pick) の実装 (`src/runner.mjs`)**: インターセプターを削除せず、`event` オブジェクト全体を転送する代わりに、`content.value`, `thought.description`, `tool_call_request.args` 等、**SSE の構築に絶対に必要な最小限のプリミティブ値のみを抽出**して送るように改修しました。
    - これにより、万が一ライブラリ側で巨大な内部状態（`AgentConfig` や `History` 等）を持つイベントが発生しても、IPC 転送時のシリアライズ対象からは外れるため、メモリ爆発は物理的に発生しなくなりました。

### 【検証：デフォルトのヒープ制限下での安定稼働】
ユーザー指示に基づき、根本原因の解決を証明するため、**`--max-old-space-size=4096` によるメモリ増設は撤回（削除）**しました。
- 結果として、Node.js デフォルトのメモリ制約（約2GB）に戻した状態でも、ツール呼び出しに伴う OOM クラッシュが発生しなくなったことを確認しました。
- これにより、「メモリ増設による対症療法」ではなく、「データ肥大化の遮断による根本治療」が有効であることが実証されました。
