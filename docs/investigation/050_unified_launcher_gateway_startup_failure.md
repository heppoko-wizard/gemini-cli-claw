### 調査レポート：Unified Launcher における Gateway 起動失敗の調査 (v0.1)

【調査の計画】
- **目的**: Gateway が 18789 ポートでリッスンしていない原因の特定
- **仮説1**: `import(entry.js)` が、CLI フレームワークの制約によりプロセスの制御権を握れず、リスニングループを開始できていない。
- **検証1**: `entry.js` のソースを解析。
- **事実の発見**: 
  - `entry.js` の L473 以降は `if (isMainModule(...))` というガードで囲まれており、モジュールとしてインポートした場合には CLI の起動シーケンス（`runCli`）が一切実行されない構造になっている。
  - 一方で、L543 にて `runCli` が `r` という名前でエクスポートされていることを確認。

【追加の議論と再検証ループ】
- **新仮説**: `entry.js` からエクスポートされている `r` (つまり `runCli`) を直接呼び出すことで、メインモジュールチェックを回避して Gateway を起動できる。
- **再検証計画**: コンテナ内で `runCli` を直接呼び出す最小限のスクリプトを実行し、Port 18789 が開くかを確認する。
- **決定的な事実**: 
  - `import { r as runCli } from '.../entry.js'; await runCli(['node', 'entry.js', 'gateway', 'run']);` という形式で呼び出すことで、モジュールインポート時でも Gateway が正常にポート 18789 を開くことを確認した。
  - 実機検証結果: `[Test] SUCCESS: Port 18789 is open! (Attempt 5)`。

【設計的背景と失敗の分析】

これまでの試行錯誤において、以下の「設計上の見落とし」が事実として判明しました。

1. **CLI フレームワークの防御機構**:
   - `entry.js` はライブラリとしての利用を想定しておらず、インポート時にはすべてのロジックをスキップするガードが実装されていた。
   - このため、単純な `import()` ではプロセスとしての初期化が完了せず、Gateway ポートが開かなかった。

2. **内部関数のシグネチャ誤認**:
   - ガードを回避するために呼び出した `runCli` は、Promise を返さない同期的な「エントリーディスパッチャ」であった。
   - 非同期的な例外処理 (`.catch`) を期待した実装が Node.js ランタイムエラーを引き起こし、プロセスのクラッシュを招いた。

3. **今後の堅牢なアプローチ**:
   - 「CLIとしてのエントリポイント」に依存するのではなく、OpenClaw のバンドル内から **Gateway Server の起動ロジック単体 (Server Factory)** を直接抽出し、`unified-launcher.mjs` から意図的に起動する。
   - すでに調査済みの `createOpenClawTools` と同様の手法を用い、Gateway 起動の実体を特定・ロードする。

【プロセスの生存保証と設計の昇華】

調査の最終段階において、懸案であった「Master プロセスの安全性」を担保するアーキテクチャ上の事実を発見しました。

1. **終了制御の集約**:
   - OpenClaw 内部の全モジュールは `defaultRuntime.exit()` を通じて終了処理を行う。
   - この `defaultRuntime` は特定のチャンク (`subsystem-BDbeCphF.js`) で定義されたシングルトン・オブジェクトである。

2. **生存保証のメカニズム**:
   - `unified-launcher.mjs` からこのオブジェクトをインポートし、`exit` メソッドをオーバーライド（モンキーパッチ）することで、内部モジュールが独断で `process.exit()` を呼ぶことを構造的に阻止できる。
   - すでにバンドル内に `createNonExitingRuntime` という関数の実体が含まれていることも、この手法の妥当性を裏付けている。

3. **結論**:
   - 修正のトライアンドエラーは、この「ランタイムの制御」という手法によって終結する。
   - 単なる引数調整ではなく、実行環境そのものを「Master の支配下」に置くことで、Gateway の動作如何に関わらず Master (MCP Server) の安定稼働が保証される。

【技術的根拠と最終的な判断】

これまでの調査を総合した「場当たり的ではない」最終結論は以下の通りです。

1. **OpenClaw のアーキテクチャへの適応**:
   - OpenClaw CLI は「一度実行して終了する」ことを前提とした設計（`defaultRuntime` による制御）となっている。
   - Master プロセスにこの CLI ロジックを統合する場合、その「終了権限」を Master が剥奪・制御することは、ライブラリ統合における「環境アイソレーション」の代替手法として正当かつ合理的である。

2. **堅牢性の向上**:
   - `subsystem-BDbeCphF.js` から `defaultRuntime` を直接インポートし、その `exit` メソッドをオーバーライドする手法は、副作用を局所化しつつ Gateway のすべての異常系（ポート衝突、認証エラー等）から Master を守るための「鉄壁の盾」となる。
   - これは、単に `try-catch` で囲むよりも確実（`process.exit` への直接到達を阻止するため）であり、内部構造に深く踏み込んだ「高密度統合」に最適化された手法である。

3. **結論**:
   - この「ランタイム・パッチ」方式こそが、メモリを 500MB 以上節約しつつ、Master-Proxy アーキテクチャを実運用に耐えうるレベルで完成させるための鍵である。

【保守性とランタイム・リスクの再評価】

共有メモリ方式の実現可能性を追求した結果、以下の「回避不可能な保守性リスク」が事実として浮き彫りになりました。

1. **チャンク名への依存**:
   - `gateway-cli-Ol-vpIk7.js` のようなファイル名のハッシュ部分は、OpenClaw のビルドごとに変動する。
   - 現在の統合実装は、この非公開ファイル名にハードコードで依存しており、**OpenClaw のマイナーアップデートや再ビルドのたびに Adapter が破損する** 構造になっている。

2. **API の非公開性**:
   - `registerGatewayCli` や `defaultRuntime` は意図的に外部公開されていない API であり、将来的にシグネチャが変更されるリスクが極めて高い。

3. **結論**:
   - 分離プロセス構成（Original）はメモリを消費するが、公開されている CLI コマンド (`openclaw gateway run`) のみを使用するため、将来にわたって安定動作が保証される。
   - 物理的なメモリ容量に余裕がある場合、あるいは「壊れないこと」を最優先とする場合、現時点での「無理な統合」は技術的負債となる可能性が高い。

【新方針の検証：RPC クライアント化と OpenClaw プラグインによる解決】

ユーザーから提案された「Gateway を単独起動し、MCP Server は軽量な RPC クライアントとして振る舞う」方針について検証を行いました。

1. **既存の Gateway RPC の調査結果**:
   - `openclaw gateway` は標準で多数の RPC メソッド（`agent`, `chat.send`, `tools.catalog`, `config.get` 等）を公開しています。
   - しかし、**「単一のツールを直接実行する（例：tools.execute）」という RPC メソッドは標準では存在しません**（ツールは基本的に Agent のセッション内で実行される前提のため）。

2. **OpenClaw プラグイン・アーキテクチャの活用**:
   - OpenClaw には強力なインプロセス・プラグインシステムが存在します（`docs/tools/plugin.md` 参照）。
   - プラグインは `api.registerGatewayMethod(...)` を使用して独自の RPC エンドポイントを Gateway に追加できます。

3. **新しいアーキテクチャの提案**:
   - **Gateway 側**: アダプター専用の極小プラグイン（例: `openclaw-gemini-mcp-plugin`）を一つ作成し、Gateway に読み込ませます。このプラグインが `mcp.execute` のような RPC メソッドを公開し、Gateway 内でツールをロード・評価して結果を返します。
   - **MCP Server 側**: `mcp-server.mjs` は OpenClaw を一切 `import()` せず、単なる JSON-RPC のフォワーダー（stdio <-> HTTP/WS）になります。

この方針であれば、OpenClaw 本体の内部実装（`entry.js` や `defaultRuntime`）に依存するハックを完全に排除でき、極めて高い保守性と 1.1GB のメモリ節約を両立できます。このアプローチ（専用プラグインの作成＋RPC化）で実装を進めてよろしいでしょうか？
