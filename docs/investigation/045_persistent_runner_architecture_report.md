### 調査レポート：Persistent Runner (常駐型) 移行によるツールロード税解消への道のり

【調査の道筋（仮説と検証のトレイル）】
- **仮説**: 現在は `runner.mjs` が1リクエストごとに終了し（Disposable）、それに伴い Gemini CLI が毎回ゼロから MCP サーバーのロード（6-10秒）を行っている。プロセスを `process.exit` させず常駐化させれば、この起動税は理論上ゼロになるはずである。
- **検証**: `grep_search` および `view_file` を用いて、`process.exit` の呼び出し箇所、およびプロセスの終了イベント (`close` / `exit`) に依存している上位レイヤー（Pool, Streaming）の処理を追跡。
- **事実の発見1 (runner.mjs)**:
  `runner.mjs` は受信メッセージ (`type: 'run'`) の処理関数内で `await runNonInteractive(...)` を呼び出し、完了した直後に `process.exit(ExitCodes.SUCCESS)` を強制発行している。
- **事実の発見2 (streaming.js)**:
  `streaming.js` 内の `runGeminiStreaming` は、プロセスが自ら終了すること (`runner.on('close')`) を検知して `res.end()`（SSE の終了シグナル `[DONE]`）をクライアントに送信している。つまり、「クライアントへの回答完了＝プロセスの死」という密結合なアーキテクチャになっている。
- **事実の発見3 (runner-pool.js)**:
  `runner.once('exit')` イベントをリッスンし、「死んだから次を新しく生む」という使い捨て専用の補充プールロジックになっている。貸出（Acquire）はあるが、返却（Release）の概念が存在しない。
- **事実の発見4 (runner.mjs - 致命的な副作用の予兆)**:
  `runner.mjs` において、`geminiClient.sendMessageStream` のモンキーパッチ（イベントインターセプト）が「`run` メッセージを受信するたびに行われる」構造になっている。プロセスを生存させて次に再利用した場合、メソッドが無限にラップ（多重フック）され、スタックオーバーフローやメモリリークを引き起こすことが実装の記述から判明した。
- **事実の発見5 (streaming.js - リスナーの重複)**:
  `streaming.js` でリクエストごとに `runner.on('message', ...)` と `runner.on('close', ...)` をアタッチしているため、同じプロセスを再利用すると、前のリクエストのリスナーが残存し、メッセージが多重発火（二重送信やクラッシュ）する。

【コードベース・仕様から確認された最終的な事実】
1. 現在のアダプターは、すべてのコンポーネントが「1リクエスト＝1プロセス（使い捨て）」を前提に設計されている。
2. これを常駐型（Persistent）にするには、以下の改修が必要不可欠である：
    - **`runner.mjs`**: `process.exit` の廃止。メソッドの多重フック（モンキーパッチ）防止。完了シグナル（例: `run_complete`）の明示的な IPC 送出。
    - **`runner-pool.js`**: `Release`（プロセス返却）概念の導入。返却されたプロセスに待機中のキュー(`pendingRequests`)を引き継がせる循環ロジックへの変更。
    - **`streaming.js`**: 応答完了トリガーをプロセスの `close` ではなく、送られてくる `run_complete` メッセージに変更。また、イベントが混線しないよう、処理完了後にリスナーオブジェクト (`runner.removeListener`) を確実に剥がすクリーンアップ処理の追加。
