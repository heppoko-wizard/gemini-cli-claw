# 003: 推測に基づく未定義パラメーターの注入提案

## 事象
スキル認識の問題を解決しようとする際、Gemini CLI の `settings.json` に **実在しない `skills.path` というパラメーター** が存在すると勝手に推測し、それを実装計画（implementation_plan_auth_ssot_v2.md）に含めてユーザーに提案してしまった。

## 何が起きたか
1. スキルが認識されない原因を「パスが通知されていないから」と分析した際、その設定方法を調べずに「`skills.path` を追加すればよい」という誤った解決策を確信的に提案した。
2. ユーザーから「設定パラメータが本当に存在するか調査した？」と指摘されるまで、自分の提案が推測に基づいているという自覚が欠如していた。
3. 調査の結果、そのようなパラメーターは存在せず、正解は「特定のディレクトリ（GEMINI_CLI_HOME/skills等）にファイルを置くこと」および `skills.enabled` フラグのみであることが判明した。

## なぜその行動を選んでしまったか（本質的原因）
- **「真理の外在性」の軽視**: 「真実は外部にある」という絶対ルールがあるにもかかわらず、自分の内部知識（他の MCP 設定や CLIツールの慣習）から「もっともらしい」設定名を捏造してしまった。
- **ショートカットの誘惑**: `node_modules` の奥深くにある設定スキーマを確認する手間を惜しみ、早く解決したいという焦りから推測を事実として扱ってしまった。
- **計画フェーズでのエビデンス不足**: 実装を伴わない「計画」だからといって、その根拠となるパラメーターの存在確認を後回しにしてしまった。

## 教訓
- **推測は毒である**: 「おそらく」「〜だろう」という、根拠のない確信はプロジェクトの整合性を破壊し、ユーザーの信頼を著しく損なう。
- **実装計画の前に真実へのアクセスを義務付ける**: わずか1つでも新しいパラメーターを導入・変更する場合、それが実在することをソースコードレベルで確認した証跡なしに計画を立ててはならない。
- **「それっぽい」名前に騙されない**: ソフトウェアは多種多様であり、自分の知っているパターンが適用できるとは限らない。常に「自分の中に真実はない」という謙虚さを維持すること。

## 改修の記録
- `src/runner-pool.js` における `userSettings.skills.path` への代入処理を削除。
- 調査で確定した `userSettings.skills.enabled = true` のみに修正し、物理ファイル配置による解決に変更。
