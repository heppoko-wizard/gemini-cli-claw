# Failure Record 001: 事実確認の怠りと推測実装によるプロセス崩壊

## 1. 状況 (Context)
OpenClaw Gemini CLI Adapter の初回起動時における、デバイス自動承認（Auto-Pairing）スクリプトの実装・デバッグ中。

## 2. 何をして、何が起きたか (Action & Symptoms)
- **何をしたか**: エラーや `undefined` が出力された際、実際の外部コマンドの出力（一次情報）を確認せずに、「おそらくキー名が昔のバージョンのものから変わったのだろう」と推測。`dev.name || dev.deviceId` などのフォールバックを追加してエラーを表面上だけ回避しようとした。
- **何が起きたか**: 
  - 存在しないオブジェクトのキーを永遠に抽出しようとし続け、ブロッキング状態（無限ループ）を引き起こした。
  - エラーが表出しなくなったことで「通信が届いていない」という誤った前提調査に時間を浪費した。

## 3. 間違えに至った本質的な根本原因 (Root Cause)
1. **「LLMの内部モデル」への過信**: 自分自身の事前知識やプロンプト上のわずかな文脈から、「おそらくこういうデータ構造だろう」と決めつけてしまったこと。**「真実は外部にしかない」という原則の忘却。**
2. **「フォールバック」の悪用**: 未知のエラーやスキーマの不一致に遭遇したとき、事実の調査（Phase 2）に立ち戻るのではなく、「とりあえず動かすための防御的コード」で蓋をしたこと。これは堅牢なプログラミングではなく、単なる事実の隠蔽であった。

## 4. どのような指示があれば防げたか (Preventative Prompt)
私がLLM（記憶を持たない新しいセッション）として未知のタスクに臨む際、以下の行動原理がプロンプトとして与えられていれば、この事態は防げました。

> **【真実の確保と推測の排除に関する絶対ルール】**
> 1. **一次情報へのアクセス義務**: 未知の関数、API、CLI出力などを扱うコードを書く前には、**必ず事前検証（`view_file`, `cat`, テスト実行など）を行い、一次情報としての生データを確認せよ**。LLMの推論でデータ構造をでっち上げるな。
> 2. **隠蔽的フォールバックの禁止**: 取得データが空（`undefined` 等）になったり原因不明のエラーが出たりした場合、安易なデフォルト値（`||` 演算子や `try-catch` による握りつぶし）で逃げてはならない。その時点で直ちに実装を中断し、生データをダンプして事実を確認する「調査フェーズ」に立ち戻れ。
