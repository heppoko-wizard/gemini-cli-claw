# 失敗記録：Dockerコンテナ内コマンド実行時のハング

## 何をしたか
Dockerコンテナ内の大きなログファイル（`zwc_errors.log`）を `docker exec` と `cat` を組み合わせて取得しようとした。

## 何が起きたか
コマンドがレスポンスを返さず、45秒以上にわたってハングアップした。その後、ユーザーから「ハング対策をタイムアウト以外で行え」との警告を受けた。

## なぜその行動を選んでしまったか（本質的原因の深掘り）
1. **標準入力（stdin）の甘い認識**: `cat` は通常入力を待たないが、`docker exec` を通じて実行した場合、擬似ターミナルや標準入力の接続状態によっては、プロセスの終了検知が正常に行われず、「何か入力が続くかもしれない」という待機状態（ハング）に陥ることがある。
2. **パイプへの依存**: `| tail` をつければ出力が制限されるため、全体の処理も早まると考えてしまった。しかし、パイプ先の `tail` が終了しても、パイプ元の `docker exec` が標準入力を掴み続けている場合、プロセス全体はクローズされない。
3. **隔離環境の過信**: Docker内であれば安全にコマンドが完結すると考えてしまったが、実際にはパススルーされる入出力のハンドリングこそがハングの主因となる。

## 再発防止策
1. **入力の物理的な遮断**: 読み取り専用コマンドであっても、常に `< /dev/null` を付与して、標準入力が即座に EOF となるように強制する。
2. **非対話モードの明示**: `docker exec` の場合は `-i` (interactive) を付けつつ入力をリダイレクトするか、対話型を必要としない `-T` (疑似TTYを割り当てない) 運用を徹底する。
3. **復唱**: Docker等の外部プロセスを叩く際は、「入力遮断（`< /dev/null`）」が施されているか自問自答すること。
